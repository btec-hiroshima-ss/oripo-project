# 実装フロー

Phase 5 以降の機能実装における標準的な作業手順。

---

## 1. Issue 確認

```bash
gh issue view <番号> -R btec-hiroshima-ss/oripo-project
```

- 実装内容・要件・親 Issue との関係を確認する
- 不明点はユーザーに確認してから進む

---

## 2. ブランチ作成

```bash
git fetch origin
git checkout main && git pull origin main
git checkout -b feature/issue-{番号}-{内容}
```

- **必ず最新の `main`（Phase 5 以降は `develop`）から切る**

---

## 3. 仕様書作成（`specs/`）

`specs/TEMPLATE.md` をコピーして仕様書を作成する。

```
specs/
  {機能名}.md   ← 新規作成
```

記載内容:

| セクション | 内容 |
|---|---|
| 概要 | 機能の目的・スコープ |
| モックアップ | `specs/images/` に画像を配置して参照 |
| 機能要件 | 画面・操作・バリデーション等 |
| API | Route Handler を使う場合のエンドポイント定義 |
| データモデル | 使用テーブル・カラム・新規追加の有無 |
| 受け入れ条件 | テストの元になる条件（箇条書き） |

**仕様書をユーザーにレビュー・承認してもらってから実装へ進む。**

---

## 4. DB マイグレーション作成（必要な場合）

新規テーブル・カラム追加が必要な場合のみ。

```bash
# ファイル名: {YYYY-MM-DD}_{内容}.ts
touch src/lib/migrations/$(date +%Y-%m-%d)_{内容}.ts
```

- `up()` / `down()` を実装する
- アプリ起動時に自動適用される（`src/instrumentation.ts`）
- 適用後に `src/lib/db.types.ts` が自動更新される

---

## 5. 実装 + ユニットテスト（繰り返し）

実装前に `/check-implementation` を実行して規約を確認する。

**コンポーネント設計の基本パターン:**

```
page.tsx（Server Component）
  → DB アクセス・データ取得
  → 子コンポーネントにデータを渡す
       ├─ 表示系（'use client'）
       └─ インタラクティブ系（'use client'）
```

実装と並行してユニットテストを作成する。

```bash
# テストファイルはソースと同置
# Button.tsx → Button.test.ts

npm run test   # 実行確認
```

- 仕様書の `## 受け入れ条件` をもとに Vitest テストを生成する
- テストが通ることを確認してから次のコンポーネントへ進む

---

## 6. 手動確認（ページ完成時）

対象ページの主要機能が揃った段階で、人間が手動で確認する。

- 仕様書の `## 受け入れ条件` をチェックリストとして使う
- ブラウザで実際に操作して確認する（ツール不要）

---

## 7. 整合性チェック

`/spec-check` を実行して仕様書・実装・テストのズレがないか確認する。

- 仕様書の機能要件がすべて実装されているか
- 仕様書の受け入れ条件がすべてテストに反映されているか
- 仕様にない実装が混入していないか

ズレがある場合は対応方針をユーザーと確認してから次へ進む。

---

## 8. PR 作成

```bash
# 変更内容を確認してユーザーの承認を得てから実行
gh pr create --title "..." --body "..."
```

- **コミット・プッシュ・PR 作成の前に必ず変更内容を提示してユーザーの確認を取る**
- PR は Issue に紐づける（`Closes #番号`）
- PR タイトルはコミットメッセージ規約に従い日本語で記述する
