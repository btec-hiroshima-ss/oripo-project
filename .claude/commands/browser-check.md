作業中のブランチの仕様書に記載された受け入れ条件をクリアしているかを、ブラウザでの E2E テストで確認してください。
やり方の正本は `docs/05_develop/implementation-rules.md` の「ブラウザ E2E テスト（受け入れ条件ベース）」。

## 前提

- アプリ URL: `http://host.docker.internal:3000`（chrome-devtools MCP を使用）
- ログイン情報: ユーザー名=`Rescho` / パスワード=`rescho`

## 手順

**1. テストケースの作成**
- `git diff develop...HEAD --name-only` で変更ファイルを確認する
- 関連する `specs/{機能名}.md` の `## 受け入れ条件` を読み、**PR で追加・変更した項目を 1 項目ずつ**テストケースにする
  - 1 つの受け入れ条件に複数のビュー・操作が含まれる場合は、それぞれを別のケースにする
  - 変更が影響する既存の受け入れ条件も、回帰確認としてケースに含める
- テストケースを表にまとめる: `| # | 受け入れ条件 | 前提（テストデータ） | 操作 | 期待結果 | 結果 |`

**2. テストデータの準備**
- 必要なデータをローカル DB に投入する。投入前の状態を記録しておく
- 表示対象を選べないビュー（マイグループでしか切り替えられないビュー等）は、テスト用のマイグループを一時的に作るなどして確認できるようにする

**3. ブラウザ操作**
- `navigate_page` でアプリにアクセスし、ログインする
- テストケースを 1 つずつ実行し、OK / NG を記録する。必要に応じて DB を SQL で確認する
- 通常の画面操作では起きない条件（owner 以外の操作、存在しないレコード等）は、画面を開いた後に DB の状態を変えるなどして、実際のサーバー処理を画面から通す。どうしても画面経由で確認できないものだけ、理由を明記してユニットテストでの確認とする

**4. レスポンシブ確認**
- `resize_page` でモバイルサイズ（幅 375px）にリサイズして、テストケースを再確認する
- モバイル向けの受け入れ条件があればすべてチェックする

**5. 後片付けと結果の報告**
- 投入したテストデータを元に戻す
- テストケース表を OK / NG 付きで報告する（PR 本文にも載せる）
- NG があれば修正してから再確認する
- 仕様の解釈に疑問がある場合はユーザーに確認を求めてから進む
- 全ケース OK になったらステップ 6（push & PR 作成）へ進む
