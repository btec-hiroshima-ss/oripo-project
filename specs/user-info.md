# ユーザー情報（個人設定）

## 概要

個人設定メニューの「ユーザー情報」パネル。ログインユーザーが自分のプロフィールを閲覧し、
「ユーザー情報とパスワードを編集する」ボタンから自分の情報を編集する。

編集モーダル（`UserEditModal.tsx`）はヘッダーのアバタークリックからも開く共通コンポーネント。
導線は PR #165 で実装済みで、本 Issue ではその中身を実装する。

関連 Issue: #143（親: #140 個人設定画面）
関連仕様: `specs/settings.md`（左の選択メニュー #142）

## 機能要件

### ユーザー情報パネル（表示）

| 領域 | 内容 |
|---|---|
| パネル見出し | 人物アイコン + 「ユーザー情報」、右端に「ユーザー情報とパスワードを編集する」ボタン |
| プロフィール見出し | アバター（`InitialAvatar`）+ 氏名 + 「部署 ・ 役職」 |
| 明細テーブル | 下表の5項目 |

| 項目 | 表示内容 |
|---|---|
| ログイン名 | `turbine_user.login_name` |
| 名前 | 姓 + 名 |
| 名前（フリガナ） | 姓カナ + 名カナ |
| 部署 | 複数所属の場合は ` / ` 区切りで連結 |
| 権限 | 管理者 / 一般利用者 |

- 権限は `turbine_user_group_role` に `admin` ロールがあれば「管理者」、なければ「一般利用者」
- 役職はデータがある場合のみ「部署 ・ 役職」の形式で表示し、無ければ部署のみ表示する
  （現行 DB には役職の紐付けデータが存在しない。「仕様確認事項」2 を参照）
- 携帯電話番号は表示しない（要件定義書 2.7 の閲覧項目に含まれないため。編集モーダルでのみ扱う）

### 編集モーダル（`UserEditModal`）

ヘッダーのアバタークリック / パネルの編集ボタンのどちらからも開く。

| 項目 | 入力 | 必須 | 備考 |
|---|---|---|---|
| ログイン名 | 表示のみ | - | 変更不可（システム ID） |
| パスワード | password | ○ | 8 文字以上 |
| パスワード（確認用） | password | ○ | パスワードと一致すること |
| 姓 / 名 | text | ○ | |
| 姓（フリガナ）/ 名（フリガナ） | text | ○ | |
| 携帯電話番号（社内） | tel | - | AIPO の「電話番号（携帯）」に相当 |
| 部署 | 表示のみ | - | 変更は管理者のユーザー管理画面（要件定義書 2.6）で行う |
| 権限 | 表示のみ | - | 同上 |

AIPO の編集フォームにある メールアドレス・電話番号（外線）・電話番号（内線）・携帯メールアドレス・
顔写真 は Oripo では扱わない。要件定義書 2.6 の登録項目に含まれず、`src/lib/db.types.ts` でも
該当カラムが「不使用」と注記されているため。

**パスワード欄の初期状態:**

既存パスワードのハッシュはクライアントに渡さず、パスワード欄・確認用欄はどちらも空欄で表示する。

**バリデーション:**

| 条件 | エラーメッセージ |
|---|---|
| 必須項目が未入力 | 「{項目名}を入力してください」 |
| 姓・名・フリガナが 99 文字超 | 「{項目名}は99文字以内で入力してください」 |
| 携帯電話番号が 15 文字超 | 「携帯電話番号は15文字以内で入力してください」 |
| パスワードが 8 文字未満 | 「パスワードは8文字以上で入力してください」 |
| パスワードが 50 文字超 | 「パスワードは50文字以内で入力してください」 |
| パスワードに半角英数以外が含まれる | 「パスワードは半角英数で入力してください」 |
| パスワードと確認用が不一致 | 「パスワードが一致しません」 |

氏名 99 文字・携帯電話番号 15 文字の上限は `turbine_user` の各カラムの桁数に合わせている
（`last_name` 等は `varchar(99)`、`cellular_phone` は `varchar(15)`）。
超過を許すと Postgres 側で `value too long` 例外になり保存に失敗するため、入力側でも `maxLength` を設定する。

パスワードの文字種・最大長は `specs/login.md` のログイン時バリデーション（最大 50 文字・半角英数のみ、
いずれも AIPO 準拠）と揃える。揃えないとログインできないパスワードを設定できてしまうため。
最小 8 文字は要件定義書 3.2 のパスワードポリシーによる。

**保存時の挙動:**

- パスワードは `hashPassword()`（SHA-1 + Base64、AIPO 互換）で保存する
- 保存に成功したらモーダルを閉じ、パネルとヘッダーの表示内容を更新する
  （ヘッダーの氏名・部署も同じ Server Component 由来のため、`revalidatePath('/')` で併せて更新する）
- 保存に失敗した場合はモーダルを閉じず、モーダル内にエラーメッセージを表示して再入力できるようにする
- 送信中は保存ボタンを無効化し、二重送信を防ぐ

**ログ出力:**

`docs/05_develop/implementation-rules.md` のログ規約に従い、更新成功時に
`{ event: 'user.profile.update', userId }` を `info` で記録する。
パスワード・ハッシュ値は出力しない。

### レスポンシブ対応

| ブレークポイント | 挙動 |
|---|---|
| デスクトップ（lg 以上） | 明細テーブルは項目名（左）と値（右）の 2 カラム。モーダルは最大幅を設けて中央表示 |
| モバイル（lg 未満） | 明細テーブルは項目名の下に値を表示する 1 カラム。モーダルは画面幅いっぱい（左右に余白）で縦スクロール |

- モーダル内の `<input>` は `text-base`（16px）以上とする（iOS Safari の自動ズーム防止）

## API

Server Actions（`src/app/(main)/actions.ts`）で実装し、Route Handler は使わない。

| 関数 | 説明 |
|---|---|
| `updateUserProfileAction` | ログインユーザー自身のプロフィール（姓・名・フリガナ・携帯電話番号・パスワード）を更新する |

- 更新対象のユーザー ID はクライアントから受け取らず、必ずセッション（`getSession()`）から取得する
  （他人のプロフィールを書き換えられないようにするため）
- 閲覧データは `page.tsx`（Server Component）で `src/lib/user.ts` の関数を呼んで取得する

### `getUserProfile` と既存 `getUserDetail` の住み分け

`src/lib/user-list.ts` に既に `getUserDetail()` があるが、本機能では `src/lib/user.ts` に
`getUserProfile()` を新設する。

| 関数 | 置き場所 | 用途 | 本機能で使えない理由 |
|---|---|---|---|
| `getUserDetail()` | `user-list.ts` | ユーザー名簿ウィジェット（要件 2.5） | 氏名を SQL 側で連結しており姓・名を分離できない。`login_name`・権限・役職も持たない |
| `getUserProfile()` | `user.ts` | 個人設定のプロフィール閲覧・編集 | - |

`user-list.ts` は「他ユーザーの名簿」、`user.ts` は「ログインユーザー自身」という既存の住み分けを維持する。

`page.tsx` は既にヘッダー表示用に `getUserDetail()` を呼んでいるため、同一ユーザーに対して 2 クエリ
発生する。`getUserProfile()` は `getUserDetail()` の返す項目をすべて含むため、`page.tsx` では
`getUserProfile()` 1 本に統合し、ヘッダーへも同じ結果を渡す。

## データモデル

既存テーブルのみを使用し、新規テーブル・カラムの追加はない。

| テーブル | 用途 |
|---|---|
| `turbine_user` | ログイン名・姓名・フリガナ・携帯電話番号・パスワード |
| `turbine_user_group_role` + `turbine_role` | 権限判定（`admin` ロールの有無） |
| `turbine_group` + `eip_m_post` | 部署名 |
| `turbine_user.position_id` + `eip_m_position` | 役職名（現行データは未設定） |

**更新するカラム（`turbine_user`）:**

| カラム | 内容 |
|---|---|
| `last_name` / `first_name` | 姓 / 名 |
| `last_name_kana` / `first_name_kana` | 姓カナ / 名カナ |
| `cellular_phone` | 携帯電話番号（社内） |
| `password_value` | ハッシュ済みパスワード |
| `password_changed` | パスワード変更日時 |
| `modified` / `updated_user_id` | 更新日時 / 更新者（AIPO 互換のため更新する） |

## 仕様確認事項

実装は下記の判断で進めているが、いずれも確定ではないため要確認。

**1. 部署・管理者権限を自分で編集できるようにするか（今回は表示のみ）**

要件定義書 2.7 は「編集項目は 2.6 の登録項目に準じる」と記載しており、2.6 の登録項目には
部署・管理者権限フラグが含まれる。一方、AIPO 実機の個人設定編集フォームでは部署・役職は表示のみで、
管理者権限の項目自体が存在しない（`docs/01_current/screenshots/10_user-info-edit-form.png`）。
一般利用者が自分に管理者権限を付与できるのはセキュリティ上問題があるため、AIPO に準拠して
表示のみとした。変更は管理者のユーザー管理画面（要件定義書 2.6）で行う想定。

**2. 役職の表示（今回はモック準拠で実装するが実データは空）**

モックアップでは氏名の下に「部署 ・ 役職（主任）」が表示されているが、現行 DB には役職と
ユーザーを紐付けるデータが存在しない。

- `eip_m_position`（役職マスタ）には 主任・課長・役員 等が登録済み（position_id 122〜222）
- `turbine_user.position_id` は全ユーザー `0` でマスタのどれにも該当しない
- `eip_m_user_position.position` は 1〜335 の連番で、役職 ID ではなく並び順

AIPO 実機のスクリーンショットでも役職欄は空欄。そのため、実装はモックの形に合わせつつ、
データが無い場合は部署のみを表示する（役職が設定されれば自動的に表示される）形とした。
役職を正式に運用するのであれば、データ移行の要否を含めて検討が必要。

**3. パスワードを毎回必須にするか（今回は必須）**

AIPO 実機に準拠し、パスワードとパスワード（確認用）を必須入力とした。
このため氏名だけを直したい場合もパスワードの再入力が必要になり、UX 上の課題がある。
「空欄なら変更しない」方式に変更するかは要確認。
